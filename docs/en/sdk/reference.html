Conventions#

  • All functions follow the standard RISC-V ilp32 calling convention. Those of zxv_api.h are inline: they call the ROM through the API table, or do the work themselves with the registers (the mouse, the sample channels).
  • Functions that can fail return an int: 0 or more on success and a negative error code on failure.
  • "The drawing page" is the video page chosen with zxv_gfx_draw_page (0 at the start of a program); "the visible page" is the one chosen with zxv_set_page.
  • Registers are memory: read and write them through volatile pointers, for example *(volatile uint8_t *)(uintptr_t)ZXV_V_BORDER = 2;. Video registers take effect at the next VBLANK.
  • Each entry says since which version of the machine specification it exists and, if it is an API function, its number. A program that uses something from specification 0.2 must check the ROM's version first: see zxv_api_version. A function the ROM does not have does nothing and returns −1. What arrived in a ROM later than the first published version (0.4.0) says so too: "ROM 0.6.0 or later".
  • What is not in the ROM (the banks, the music, the libraries of sdk/lib) is compiled with your program: it has no "Since", but says which ROM it needs if it needs a particular one.

System and timing#

zxv_wait_vblank#

void zxv_wait_vblank(void);

Waits for the next VBLANK, the start of a frame: there are 60 per second (ZXV_FRAME_HZ). It is a game's clock: do one frame's work and wait for the next.

It turns interrupts on if they were off (it needs them to notice the VBLANK). Do not call it from a frame hook: the hook runs with interrupts off, and it would wait for ever.

Example

for (;;) {
    move_everything();
    draw_everything();
    zxv_wait_vblank();              /* 60 rounds a second */
}

Since: specification 0.1 · API function no. 1.

See also: zxv_set_frame_hook, zxv_time_us, the system variable ZXV_SV_FRAMES (System variables).

zxv_set_frame_hook#

void zxv_set_frame_hook(void (*fn)(void));

Makes the system call fn at every VBLANK, from the interrupt (with interrupts off), even if the program is busy with something else. It is for what has to happen every frame without fail: the music, a counter.

Parameters

Parameter Values What it is
fn a void f(void) function, or 0 The function called at every VBLANK; 0 removes the one there was. There is only one hook: setting another replaces the previous one.

Rules of the hook:

  • Keep it short: while it runs, there are no other interrupts.
  • It cannot call zxv_wait_vblank or anything that uses it (such as zxv_smp_upload), nor load a code bank: the program would stop with an error.
  • Variables it shares with the rest of the program must be volatile.
  • Remove it before your program ends. The ROM removes it when going back to BASIC, but not when going back to the system monitor.

Example

static volatile uint32_t frames;

static void every_frame(void)
{
    frames++;
}

zxv_set_frame_hook(every_frame);
/* ... the game ... */
zxv_set_frame_hook(0);              /* before ending */

Since: specification 0.1 · function no. 2.

See also: zxv_wait_vblank, zxv_music_update, the system variable ZXV_SV_FRAME_HOOK.

zxv_time_us#

uint32_t zxv_time_us(void);

A microsecond counter, which never stops and is never set. It is for measuring times and for giving the time to the sound's timed queue.

Returns: the microseconds of the counter. It wraps round every 2³² µs (about 71 minutes): compare times by subtracting them as unsigned numbers, and the subtraction comes out right even if it wrapped round in between.

Errors: none.

Example

uint32_t t0 = zxv_time_us();
do_something();
uint32_t elapsed = zxv_time_us() - t0;     /* in µs, even if it wraps round */

Since: specification 0.1 · function no. 3.

See also: zxv_wait_vblank, zxv_clock_get (the date and time).

zxv_api_version#

uint32_t zxv_api_version(void);

The version of the machine specification that the ROM the program runs on meets. It is what says which functions and which system variables there are.

Returns: major << 16 | minor. The current ROM gives 3 (version 0.3); earlier ones, 2 (0.2) or 1 (0.1). It is the same as the system variable ZXV_SV_VERSION. ZXV_SPEC_VERSION (3) is the version of the headers you compile with, not that of the machine.

Errors: none.

Checking the version. A program compiled with this SDK can end up on a machine with an older ROM. Before using what arrived with specification 0.2 (the pattern of the shapes, zxv_m7_draw_map, zxv_m7_affine, the banks, zxv_report_error messages of more than 47 bytes...), check that the ROM has it. With a 0.1 ROM, a 0.2 function does nothing (returns −1), and the banks give ZXV_E_ACCESS. The same with what arrived with 0.3 (JOY2, JOY3, fire 4, L and R): with an older ROM it reads 0. Specification 0.3 is that of ZX-V 0.12.0 and later; 0.2, that of 0.11.0; 0.1, that of the earlier ones.

The ZX-V version is not this. ZXV_VERSION (from zxv_version.h, for example "0.12.0") is the version of the ZX-V programs (the ROM, the emulator and the firmware, which are released together) this SDK came out with. It is a fixed string compiled into your program: it does not say which ROM the machine has, and many ZX-V versions meet the same specification. To know what the machine can do, use zxv_api_version.

Example

static const uint8_t pattern[8] = { 0xAA, 0x55, 0xAA, 0x55, 0xAA, 0x55, 0xAA, 0x55 };

if (zxv_api_version() >= 2)         /* specification 0.2 or later */
    zxv_gfx_pattern(pattern, 0);    /* patterned shapes */

Since: specification 0.1 · function no. 0.

See also: Constants, API function numbers.

Screen and text#

zxv_set_mode#

void zxv_set_mode(int mode);

Changes the video mode from the next VBLANK and clears the drawing page with the paper colour of the text (see zxv_text_colors). The text cursor goes back to the top left.

Parameters

Parameter Values What it is
mode 0 or 1 0: 256 × 192 pixels; 1: 512 × 384. Only bit 0 counts (2 is mode 0, 3 is mode 1).

Mode 1 uses the whole video page (96 KB): whatever the program has in the hidden VRAM (ZXV_VRAM0_DATA, ZXV_VRAM1_DATA, see Memory map) is lost. In mode 0 with the virtual playfield (ZXV_V_VSIZE), the whole virtual page is cleared.

Constant Value Meaning
ZXV_MODE0_W, ZXV_MODE0_H 256, 192 The mode 0 screen
ZXV_MODE1_W, ZXV_MODE1_H 512, 384 The mode 1 screen
ZXV_SCREEN_PIXELS(mode) 24,576 or 98,304 The bytes of the pixels of a screen (4 bits per pixel)
ZXV_SCREEN_SIZE(mode) 24,580 or 98,308 The size of a screen saved without palette: the header (ZXV_SCREEN_HEAD, 4) and the pixels; with palette, ZXV_SCREEN_SIZE_F (see The .zxv file format)

Example

zxv_text_colors(7, 1);              /* the blue paper... */
zxv_set_mode(1);                    /* ...fills the 512 x 384 screen */

Since: specification 0.1 · function no. 4.

See also: zxv_set_page, zxv_cls, the ZXV_V_MODE register (Video registers).

zxv_set_page#

void zxv_set_page(int page);

Chooses the video page that is shown, from the next VBLANK (writes ZXV_V_PAGE). It does not change the page you draw on: for double buffering, you draw on one and show the other.

Parameters

Parameter Values What it is
page 0 or 1 The page. Only bit 0 counts.

Example

int drawing = 1;
for (;;) {
    zxv_gfx_draw_page(drawing);     /* draw on the one not shown */
    draw_everything();
    zxv_set_page(drawing);          /* and show it at the VBLANK */
    zxv_wait_vblank();
    drawing ^= 1;
}

Since: specification 0.1 · function no. 5.

See also: zxv_set_mode, zxv_gfx_draw_page (Graphics engine).

zxv_cls#

void zxv_cls(int colour);

Fills the drawing page with a colour and moves the text cursor to the top left. It does not change the text colours.

Parameters

Parameter Values What it is
colour 0–15 The colour (the palette). Only the low 4 bits count.

In mode 0 with the virtual playfield (ZXV_V_VSIZE) it fills the whole virtual page.

Example

zxv_cls(1);                         /* all blue */

Since: specification 0.1 · function no. 6.

See also: zxv_set_mode, zxv_gfx_rect (Graphics engine).

zxv_plot#

void zxv_plot(int x, int y, int colour);

Sets one pixel of the drawing page. It is simple and slow: to draw a lot, use the graphics engine.

Parameters

Parameter Values What it is
x, y inside the page The pixel, counting from the top left. A point outside the page is not drawn (it is not an error).
colour 0–15 The colour. Only the low 4 bits count.

Example

for (int x = 0; x < ZXV_MODE0_W; x++)
    zxv_plot(x, 96, 2);             /* a red line */

Since: specification 0.1 · function no. 7.

See also: zxv_gfx_line (Graphics engine).

zxv_print_char, zxv_print_str#

void zxv_print_char(int c);
void zxv_print_str(const char *s);

Print a character or a string at the text cursor of the drawing page, in cells of 8 × 8 pixels, with the colours of zxv_text_colors, and move the cursor past it. At the end of a line they carry on in the next one, and when the text goes past the last row, the screen scrolls up one row.

Parameters

Parameter Values What it is
c a Unicode code point The character ('A', 0xF1 for ñ...).
s zero-terminated UTF-8 string The text. UTF-8 is the encoding of C source files, so you can write "¡Hola!" in your program.

The characters that are drawn:

Character What comes out
ASCII 32 to 126 The character
© (0xA9) © (also with 127)
á é í ó ú ü ñ, Á É Í Ó Ú Ü Ñ, ¿, ¡ The letter, from the ROM's font
'\n' or '\r' Goes to the start of the next line. Each one is a new line: "\r\n" leaves a blank line
'\b' Deletes the previous character and moves back (in column 0, nothing)
Any other ('\t', other control characters, other letters) ?

A malformed UTF-8 sequence comes out as ?.

The rows and columns depend on the mode: 32 × 24 cells in mode 0 and 64 × 48 in mode 1 (in mode 0 with the virtual playfield, those of the virtual page).

Example

zxv_print_str("Lives: ");
zxv_print_char('0' + lives);
zxv_print_char('\n');

Since: specification 0.1 · functions no. 8 and 9.

See also: zxv_text_colors, zxv_text_at, the fonts of zxv_font.h.

zxv_text_colors, zxv_text_at#

void zxv_text_colors(int ink, int paper);
void zxv_text_at(int col, int row);

zxv_text_colors sets the colours of the text that zxv_print_char and zxv_print_str write from then on: each cell is filled with the paper and the character drawn in the ink. zxv_text_at moves the text cursor to another cell.

Parameters

Parameter Values What it is
ink 0–15 The ink. Only the low 4 bits count.
paper 0–15 The paper. It is also the colour zxv_set_mode clears the screen with.
col 0–31 in mode 0, 0–63 in mode 1 The column, from 0 on the left.
row 0–23 in mode 0, 0–47 in mode 1 The row, from 0 at the top.

A position off the screen is not an error: what falls outside is not drawn, and if the cursor is below the last row, the next character scrolls the screen up and carries on in the last row.

Every program starts with black on white (0 and 7) and the cursor at the top left, whatever the previous one left: the ROM sets them like that when it loads each .zxv. zxv_cls and zxv_set_mode also put the cursor back at the top left.

Example

zxv_text_colors(14, 1);             /* bright yellow on blue */
zxv_text_at(8, 10);
zxv_print_str("¡Hola, señor Núñez!");

Since: specification 0.1 · functions no. 53 and 54.

See also: zxv_print_char, zxv_print_str, Palette.

Keyboard, joystick and mouse#

zxv_key_get#

int zxv_key_get(void);

Takes the next key from the key queue. The queue keeps the key presses in order (64 at most; if it fills up, new ones are lost), so none is missed even if the program is slow to look. To know which keys are held down now (a game), read the input registers ZXV_I_KEYMAP or use zxv_input.h.

Returns: the code of the key (table), or −1 if the queue is empty.

Code Key
Unicode code of the character A key that types a character, with the keyboard layout ('a', 'A', 'ñ' = 0xF1, '@'...)
0x0D, 0x08, 0x09, 0x1B Enter, Backspace, Tab, Esc
ZXV_KEY_SPECIAL (0xF000) | HID code The keys that do not type (below)
Code Key Code Key
0xF03A–0xF045 F1–F12 0xF04C Delete
0xF046 Print Screen 0xF04D End
0xF047 Scroll Lock 0xF04E Page Down
0xF048 Pause 0xF04F →
0xF049 Insert 0xF050 ←
0xF04A Home 0xF051 ↓
0xF04B Page Up 0xF052 ↑
0xF068–0xF073 F13–F24

Keys held down repeat (after 500 ms, and then 20 times a second): those that type, Enter, Backspace, Tab, Delete, End, Page Down and the cursors. Accented letters cannot be typed: the accent and the letter give the plain letter. Ctrl+Alt+Delete never arrives (it restarts the machine), nor does Ctrl+Alt+F12 (the board's diagnostics page).

Errors: none.

Example

int k;
while ((k = zxv_key_get()) >= 0) {
    if (k == 0x1B)
        quit = 1;                           /* Esc */
    else if (k == (int)(ZXV_KEY_SPECIAL | 0x52))
        go_up();                            /* cursor up */
}

Since: specification 0.1 · function no. 10.

See also: Input registers, zxv_joy_read.

zxv_joy_read#

uint32_t zxv_joy_read(int n);

The state of a USB gamepad: which directions and buttons are pressed right now. It is the same as reading the registers ZXV_I_JOY0 to ZXV_I_JOY3.

Parameters

Parameter Values What it is
n 0–3 The gamepad: the first one connected is 0, the second, 1, and so on up to 3; any other value reads 0. 2 and 3 since specification 0.3 (before, they always read 0); up to ZX-V 0.11, any value other than 0 read 1.

Returns: the bits of the table, set for those pressed; ZXV_JOY_CONNECTED says there is a gamepad. A disconnected gamepad reads 0.

Constant Bit Constant Bit
ZXV_JOY_RIGHT 0 ZXV_JOY_START 7
ZXV_JOY_LEFT 1 ZXV_JOY_SELECT 8
ZXV_JOY_DOWN 2 ZXV_JOY_FIRE4 9
ZXV_JOY_UP 3 ZXV_JOY_L 10
ZXV_JOY_FIRE1 4 ZXV_JOY_R 11
ZXV_JOY_FIRE2 5 ZXV_JOY_CONNECTED 15
ZXV_JOY_FIRE3 6

ZXV_JOY_FIRE4, ZXV_JOY_L and ZXV_JOY_R since specification 0.3 (before, 0).

Direction comes from the d-pad or the left stick (past a quarter of its travel). On a PlayStation pad, ✕, ○, □ and △ are fire 1 to 4, L1 is L and R1 is R; Share/Create is Select and Options is Start. On an Xbox pad (360, One or Series), A, B, X and Y are the fire buttons, LB and RB are L and R. On a generic pad, buttons 1–4 are the fire buttons, 5 is L, 6 is R, 9 is Select and 10 Start.

Errors: none.

Example

uint32_t j = zxv_joy_read(0);
if (j & ZXV_JOY_LEFT)
    x--;
if (j & ZXV_JOY_FIRE1)
    fire();

Since: specification 0.1 · function no. 11.

See also: zxv_key_get, zxv_input.h.

The mouse: zxv_mouse_t, zxv_mouse_init, zxv_mouse_update#

typedef struct {
    int x, y;                   /* the pointer, in pixels */
    int wheel;                  /* the wheel, accumulated (positive upwards) */
    uint8_t buttons;            /* bits 0-2: left, right and middle */
    uint16_t rx, ry;            /* internal: the counters at the last call */
    uint8_t rw;
} zxv_mouse_t;

void zxv_mouse_init(zxv_mouse_t *p, int x, int y);
void zxv_mouse_update(zxv_mouse_t *p, int w, int h);

A pointer in pixels that follows the USB mouse, like MOUSE in BASIC. zxv_mouse_init puts the pointer at (x, y) and remembers the mouse's counters. zxv_mouse_update, once per frame, adds the movement since the last call (one mouse unit is one pixel, without acceleration), reads the buttons and the wheel, and keeps the pointer inside the area. They read the input registers ZXV_I_MOUSE_... directly; without a mouse, the pointer does not move.

Parameters

Parameter Values What it is
p The pointer, a structure of the program.
x, y Where the pointer starts.
w, h 1 or more The size of the area: the pointer stays in [0, w) × [0, h). Usually that of the screen.

Example

zxv_mouse_t m;
zxv_mouse_init(&m, ZXV_MODE0_W / 2, ZXV_MODE0_H / 2);
for (;;) {
    zxv_mouse_update(&m, ZXV_MODE0_W, ZXV_MODE0_H);
    if (m.buttons & 1)
        zxv_plot(m.x, m.y, 2);              /* paint with the left button */
    zxv_wait_vblank();
}

Since: specification 0.1 (they are in zxv_api.h; they are not API functions).

See also: Input registers.

Sound#

The sound is two AY chips, the beeper and twelve sample channels, mixed at the output. The AY and the sample channels are written through two queues: one that plays as soon as it can (zxv_ay_write) and another in which each write carries its time (zxv_ay_event). The volumes and the stereo are in the sound registers.

zxv_ay_write#

void zxv_ay_write(int reg, int val);

Writes to a register of an AY (or of a sample channel). The write goes through a queue of 256 entries and sounds a few milliseconds later, in order with the others; if the queue is full, the function waits. Writing register 13 restarts the envelope, as on the real chip.

Parameters

Parameter Values What it is
reg 0–15, the first AY; ZXV_AY2 + 0–15 (16–31), the second The register (table). The numbers of the sample channels (ZXV_SMP_REG(ch, reg), 64–159) and ZXV_SMP_KEYON_HI and ZXV_SMP_KEYON (36, 37) also work. Other numbers are ignored.
val 0–255 The value. Bits the register does not have are dropped (register 1 only keeps 4, for example).
Register Contents
0, 1 Tone period of channel A: low 8 bits, high 4 bits
2, 3 Tone period of channel B
4, 5 Tone period of channel C
6 Noise period (5 bits)
7 Mixer: bits 0–2 = 1 turn off the tone of A, B, C; bits 3–5 = 1 turn off the noise of A, B, C
8, 9, 10 Volume of A, B, C (0–15); bit 4 = follow the envelope
11, 12 Envelope period: low and high byte
13 Envelope shape (0–15)

The tone frequency is 1,773,447.5 / (16 × period) Hz; the envelope repeats every 256 × period / 1,773,447.5 seconds. Both chips start silent, and the ROM silences them when a program goes back to BASIC.

Example

zxv_ay_write(0, 252);               /* A 440 Hz on channel A: period 252 */
zxv_ay_write(1, 0);
zxv_ay_write(7, 0x3E);              /* only the tone of A */
zxv_ay_write(8, 15);                /* at full volume */

Since: specification 0.1 · function no. 12.

See also: zxv_ay_event, Constants, Music and effects.

zxv_beeper_event#

void zxv_beeper_event(int level);

Sets the beeper to a level at exactly the current time plus ZXV_BEEP_LATENCY_US (2000 µs). The changes go through the timed queue (256 entries, shared with zxv_ay_event); if it is full, the function waits. That way the beeper sounds with microsecond precision, even if the program does not call at exactly the right time.

Parameters

Parameter Values What it is
level 0, or anything else 0, low; any other value, high (1).

For simple sounds you can write the ZXV_S_BEEPER register instead; both ways add up. With the music of zxv_music.h playing, use zxv_beeper_event_at: this one uses the current time, and the music has already queued its own times ahead.

Example

for (int i = 0; i < 200; i++) {     /* a 1 kHz beep */
    zxv_beeper_event(i & 1);
    uint32_t t = zxv_time_us();

        ;
}

zxv_ay_event#

void zxv_ay_event(uint32_t t_us, int reg, int val);

Writes to a register of an AY (or of a sample channel) at an exact time: t_us plus 2 ms (ZXV_BEEP_LATENCY_US). It goes through the timed queue, the same as the beeper's. It is meant for digitised sound and for music: see the digital example.

Parameters

Parameter Values What it is

}

Sample channels#

Twelve channels that play samples from the sound memory, which is in the Pico ULA, like an Amiga's Paula: music from MOD files, recorded effects and voices, or a byte you write that sounds at once (the DAC). Each channel has its note (its step), its volume and its pan, and mixes with the two AYs. In the emulator they sound the same, with the same code.

The sound memory has two parts, and the program fills it with zxv_smp_upload:

From To What
0 ZXV_SMP_MEM (0x18000, 96 KB) The samples. A sample has to be entirely here
ZXV_SMP_TABLE (0x18000) ZXV_SMP_SOUND_MEM (0x18C00) The sample table: 256 entries (ZXV_SMP_SLOTS) of 12 bytes (ZXV_SMP_SLOT_SIZE), filled with zxv_smp_define

An entry of the table (all with the low byte first):

Bytes Field
0–2 Where the sample starts in the sound memory (24 bits)
3 The format: ZXV_SMP_PCM8 (0) or ZXV_SMP_ADPCM (1)
4–7 How many samples it has
8–11 The sample the loop starts again from; if it is the length or more, there is no loop

An entry that is not valid (another format, length 0, a sample that does not fit in the 96 KB) gives no error: the sample does not sound.

The formats:

  • ZXV_SMP_PCM8: one signed byte per sample (−128 to 127). It takes any step.
  • ZXV_SMP_ADPCM: IMA ADPCM, in independent blocks of 64 samples (ZXV_SMP_ADPCM_BLOCK) in 36 bytes (ZXV_SMP_ADPCM_BYTES): the first sample in 16 signed bits (bytes 0–1), the step index (byte 2, 0–88), a zero byte and the other 63 in 4 bits, from byte 4, the even-numbered one in the low 4 bits. It sounds like 16 bits and takes a little over half of 8 bits. Each sample is worked out from the one before, so a high note also decodes the ones it skips: an ADPCM channel goes no higher than step 2.0 (ZXV_SMP_ADPCM_MAX_STEP, an octave above how it was recorded); a higher step counts as 2.0. A sample of n samples takes (n + 63) / 64 × 36 bytes. smp_adpcm_encode, from sdk/sound/smpsynth.c, encodes; the samples example has its own encoder.

The sound of a channel:

  • Interpolation, on by default, smooths the low notes; the last sample of a loop goes towards the first sample of the loop, so a short waveform in a loop sounds round. ZXV_SMP_NOINTERP turns it off (the raw sound of an Amiga).
  • Direct mode (ZXV_SMP_DIRECT) plays the value of ZXV_SMP_OFFSET as it is written, with no sample: a signed 8-bit DAC, like the SpecDrum. With zxv_ay_event, each value sounds at its time.
  • The volume of all of them is the ZXV_S_SMP_VOLUME register (0–255, 255 at power-on; the ROM does not reset it between programs): one channel at full volume is as loud as one AY channel, and twelve at full volume saturate.

The registers of a channel. They are written through the AY queues with zxv_smp_write(ch, reg, val) (or ZXV_SMP_REG(ch, reg) with zxv_ay_write and zxv_ay_event), and read at ZXV_S_SMP_REGS + 8 × channel + register (Sound registers).

Register Number What it is
ZXV_SMP_SLOT 0 The sample: an entry of the table (0–255). Counts when it is started
ZXV_SMP_VOL 1 Volume, 0–64 (more counts as 64). Changes at once
ZXV_SMP_PAN 2 Pan: 0 left, 128 centre, 255 right. Changes at once
ZXV_SMP_CTRL 3 Writing it: ZXV_SMP_KEY (0x01) starts the sample from ZXV_SMP_OFFSET and ZXV_SMP_STOP (0x02) stops it. ZXV_SMP_NOINTERP (0x04) and ZXV_SMP_DIRECT (0x08) stay until the next write of CTRL: each write sets or clears them
ZXV_SMP_STEP 4–6 Three bytes, from low to high (8.16): how far it moves for each output sample, which runs at 48 kHz. 0x10000 (1.0) is the sample at 48 kHz. Changes at once, also with the sample playing
ZXV_SMP_OFFSET 7 Where it starts when started, in steps of 256 samples (a MOD's 9xx). In direct mode, the value that sounds (signed)

zxv_smp_upload#

int zxv_smp_upload(uint32_t dst, const void *src, uint32_t len);

Copies bytes from the RAM to the sound memory, and waits until they are there. The copy goes through the link with the ULA, a piece every frame, so a big one takes several frames. It also serves to write the sample table directly (from ZXV_SMP_TABLE).

Parameters

Parameter Values What it is
dst 0 to ZXV_SMP_SOUND_MEM Where, in the sound memory.
src in the RAM (0x2000_0000–0x2006_FFFF) Where from. Your program's data (const too) is in the RAM; the ROM does not work (the emulator accepts it, the board does not).
len a multiple of 4; 0 is valid How many bytes. dst + len cannot go past ZXV_SMP_SOUND_MEM.

Returns: ZXV_OK, or an error.

Errors

Error When
ZXV_E_RANGE len is not a multiple of 4; it does not fit (dst + len goes past ZXV_SMP_SOUND_MEM); src (all of it) is not in the RAM; or the ULA does not answer within a second (a ULA firmware older than the sample channels). Nothing is copied, or not all of it.

It uses zxv_wait_vblank: do not call it from a frame hook.

Example

static const int8_t wave[32] = { 0, 24, 48, 70, 90, 106, 117, 125,
                                 127, 125, 117, 106, 90, 70, 48, 24,
                                 0, -24, -48, -70, -90, -106, -117, -125,
                                 -127, -125, -117, -106, -90, -70, -48, -24 };

if (zxv_smp_upload(0, wave, sizeof wave) < 0)
    zxv_report_error(0, "No sample channels");

Since: specification 0.1, ROM 0.10.0 or later (it is in zxv_api.h; it uses the registers ZXV_S_SMP_SRC, _DST, _LEN and _UPLOAD).

See also: zxv_smp_define, zxv_music_samples.

zxv_smp_define#

int zxv_smp_define(int slot, uint32_t addr, int fmt, uint32_t len, uint32_t loop);

Fills an entry of the sample table: where a sample that is already in the sound memory is, its format and its loop. It is a 12-byte zxv_smp_upload. A channel already playing it carries on with the old one: the entry is read when the sample is started.

Parameters

Parameter Values What it is
slot 0–255 The entry of the table.
addr 0 to 0x17FFF Where the sample starts in the sound memory.
fmt ZXV_SMP_PCM8 or ZXV_SMP_ADPCM The format.
len 1 or more How many samples it has (not bytes). It has to fit entirely in the 96 KB.
loop 0 to len − 1, or len or more The sample it starts again from when it reaches the end; len or more: no loop, it stops at the end.

zxv_smp_play#

void zxv_smp_play(int ch, int slot, uint32_t step, int vol, int pan);

Plays a sample on a channel, now, from the start. It is zxv_smp_prepare and a write of ZXV_SMP_KEY to ZXV_SMP_CTRL: through the AY queue, in order with everything else. If the channel was playing something else, it cuts it.

Parameters

Parameter Values What it is
ch 0–11 The channel. Another value writes where it should not: do not use it.
slot 0–255 The entry of the table.
step 0 to 0xFFFFFF (8.16) The step: zxv_smp_step(hz) for a sample recorded at hz to sound at its own pitch; twice that, an octave higher. In ADPCM, up to 0x20000.
vol 0–64 The volume (more counts as 64).
pan 0–255 The pan: 0 left, 128 centre, 255 right.

Since it writes ZXV_SMP_CTRL with only ZXV_SMP_KEY, it clears ZXV_SMP_NOINTERP and ZXV_SMP_DIRECT on the channel. To play without interpolation, write zxv_smp_write(ch, ZXV_SMP_CTRL, ZXV_SMP_NOINTERP) afterwards.

Example

zxv_smp_play(0, 0, zxv_smp_step(440 * 32), 64, 128);   /* the 32-sample wave: 440 Hz */

Since: specification 0.1, ROM 0.10.0 or later (it is in zxv_api.h).

See also: zxv_smp_stop, zxv_smp_prepare, zxv_smp_start, zxv_music_smp_fx (with the music playing).

zxv_smp_prepare, zxv_smp_start#

void zxv_smp_prepare(int ch, int slot, uint32_t step, int vol, int pan);

zxv_smp_prepare sets up a channel just like zxv_smp_play (sample, step, volume, pan and from the start), but without starting it. zxv_smp_start starts the channels it is given together, on the same output sample, whether prepared or not (from ZXV_SMP_OFFSET). Parameter Values What it is

Music and effects#

Declared in zxv_music.h. Build it with the files of sdk/music: it is not in the ROM (BASIC has its own copy), and it works with any ROM. The explanations and a complete example are in the guide.

The essentials:

  • It plays at its own tempo: 50 steps per second, as on the Spectrum (a .zxm, at its tempo; a VGM, at its waits), even though the machine runs at 60 frames per second. Each step goes to the AYs at its time with zxv_ay_event, and only the registers that change.
  • It has to be kept going: zxv_music_update prepares the next 35 ms (ZXV_MUSIC_AHEAD_US). Call it every frame, or from the frame hook (and then only from there). Without it nothing sounds, not the effects, nor the silence when stopping.
  • The library copies nothing: the module, the effect bank and the work memory of a .vgz must stay in memory while they play.
  • The timed queue goes in order: if the program uses it too, its times have to be 35 ms ahead, like the music's (zxv_beeper_event_at), or be mixed in with zxv_music_update_until.
  • The channels: a one-AY module plays on the first chip (or on the second, with ZXV_MUSIC_AY2); TurboSound, a .zxm or a two-AY VGM, on both. AYFX effects go on channels A, B and C of either chip, over the music. A .zxm plays its sample tracks on the sample channels from 0 on.

zxv_music_play#

int zxv_music_play(const void *data, uint32_t size, int flags);

Starts playing a module, from the beginning, instead of whatever was playing. It recognises it by its contents, not by the file name.

Parameters

Parameter Values What it is
data The module, whole in memory, and it must stay there while it plays.
size bytes Its size.
flags 0, ZXV_MUSIC_LOOP, ZXV_MUSIC_AY2, or both ZXV_MUSIC_LOOP: at the end, it goes on from its loop position (without it, it stops). ZXV_MUSIC_AY2: a one-AY module plays on the second chip (on a two-AY one, it does not count).

Returns: the format (ZXV_MUSIC_PT3...), or ZXV_MUSIC_NONE if it does not recognise it; then it plays nothing (and whatever was playing has already stopped).

  • A .zxm uploads its samples to the sound memory before starting (it waits until they are there; do not call it from a frame hook), wherever zxv_music_samples says.
  • A .vgz is decompressed while it plays, with the memory you give it with zxv_music_work: without it, it gives ZXV_MUSIC_NONE. Of a VGM only the AY chips play; writes to other chips are skipped.
  • The samples of the previous song go silent at once.

Example

extern const uint8_t song[];
extern const uint32_t song_len;

if (zxv_music_play(song, song_len, ZXV_MUSIC_LOOP) == ZXV_MUSIC_NONE)
    zxv_report_error(0, "The song is not valid");

Files and folders#

There are three drives: SD: (the SD card), ROM: (the built-in read-only drive, in the flash) and EXT: (the external drive: a folder served by another device, see The EXT: drive). The functions are the same for all three.

  • Up to 8 files and 4 folders can be open at once on each drive. The file of a program with banks is open while it runs, and counts.
  • File numbers say which drive they belong to: 0–7 on SD:, 8–15 on ROM: and 16–23 on EXT:; folder numbers, 0–3, 4–7 and 8–11.
  • Each drive has its current folder, and one of them is the current drive (SD: at power-on).
  • Buffers must be entirely in the RAM (from 0x2000_0000 to 0x2006_FFFF: the system area, the VRAM and the user RAM) or, if the function only reads them (what is written to a file, the names), in the ROM. Otherwise the function returns ZXV_E_FAULT and does nothing.
  • On an SD card, each zxv_file_write reaches the card before returning (if the card is taken out afterwards, what was written is there). A file that is open cannot be deleted, renamed or opened again for writing. If the card is taken out, whatever was open on it only gives ZXV_E_NOCARD until it is closed.
  • On EXT: you read and write as on the card, but only while there is a server: otherwise every call returns ZXV_E_OFFLINE. If the server goes away, the first call waits 1.5 seconds and the next ones fail at once until it comes back. The server writes to a copy and replaces the file when it is closed, and it may refuse to replace or delete a file the machine did not write (ZXV_E_ACCESS).

Common errors. Besides the ones of each function, any file function can give:

Error When
ZXV_E_NOCARD The path goes to SD: and there is no card (or it does not respond); or the file or folder was opened before the card was taken out.
ZXV_E_IO The card failed to read or write, or does not have a FAT format that can be understood. Whatever was open on it is no longer valid, as when taking it out.
ZXV_E_OFFLINE The path goes to EXT: and there is no server, or it has stopped answering.
ZXV_E_FAULT A buffer or a name is not entirely in the allowed memory (above). Nothing is touched.

Paths#

  • The drive: a path may start with SD:, ROM: or EXT:, upper or lower case. After the drive, the path always goes from its root: ROM:graphics is the same as ROM:/graphics.
  • Without a drive, the path is on the current drive: relative to its current folder, or from its root if it starts with /.
  • . and .. work, and .. at the root stays at the root. Case does not matter (Level1.DAT is level1.dat).
  • Names have 1 to 63 (ZXV_NAME_MAX) printable ASCII characters, without \ : * ? " < > |, and not ending in a space or a dot. Paths, up to 255 characters (ZXV_PATH_MAX) and 64 folders deep. Otherwise, ZXV_E_NAME.
  • On the card, hidden or system files, and those with a name that does not follow these rules (with accents, or longer than 63 characters), do not appear in listings.

int zxv_file_open(const char *name, uint32_t flags);

Parameter Values What it is

int zxv_file_read(int f, void *buf, uint32_t n);

Read or write up to n bytes at the current position of the file, and move it past what was read or written. If you read code to run it, execute a fence.i instruction afterwards (or use zxv_file_load, which executes it).

Parameters

Parameter Values What it is
f a number from zxv_file_open The file.
buf n bytes in the RAM (when writing, also in the ROM) Where to read into, or what is written. When reading, buf must have room for n bytes even if the file has fewer.
n bytes How many.

Error When
ZXV_E_BADF f is not an open file.
ZXV_E_ACCESS Reading from a file opened without ZXV_O_READ; writing to one opened without ZXV_O_WRITE, or on ROM:.

(common) See Common errors. ZXV_E_FAULT if buf does not have n bytes in the allowed memory.

    zxv_file_close(f);
}

Banks#

zxv_bank.h and zxvbank.c: data that goes at the end of the .zxv itself and is loaded when needed; and, with tools/zxvbanks.py, code too. The explanations are in the guide: Banks: more data than fits at once and Code banks.

  • Data banks are added when converting the ELF: elf2zxv.py game.elf game.zxv --bank stage1=stage1.gfx --pack (with --pack, each one is compressed if that makes it smaller).
  • They are read from the program's own file, which the ROM keeps open while it runs (ZXV_SV_PROG_FILE): the current folder or drive does not matter. That file takes one of the 8 of its drive.
  • They use about 2 KB of stack.
  • They need a ROM with specification 0.2 or later; with an older one, everything gives ZXV_E_ACCESS (the program loads and runs all the same).

zxv_bank_load#

int zxv_bank_load(const char *name, void *dst, uint32_t max);

Loads a data bank into memory: it unpacks it straight into dst if it is compressed, and checks its CRC.

Parameters

Parameter Values What it is
name up to 15 characters The name of the bank, as in --bank. Here case does matter.
dst in the RAM Where it is loaded.
max bytes The room at dst. zxv_bank_size says how much is needed.

Returns: the size of the bank (unpacked), or an error.

Errors

Error When
ZXV_E_NOENT There is no data bank with that name (a code bank does not count: its bridges load it), or the program has no banks.
ZXV_E_RANGE The bank is bigger than max. dst is not touched.
ZXV_E_CHANGED The file is no longer the running program's (another version copied to the card, or rebuilt on the PC while it runs from EXT:): the program has to be loaded again.
ZXV_E_FORMAT The bank is damaged: its CRC does not match, it does not unpack properly or the file ends too soon.
ZXV_E_ACCESS The ROM is older than specification 0.2.
ZXV_E_NOCARD, ZXV_E_OFFLINE, ZXV_E_IO Those of reading the file: no card, no EXT: server, a read error.
ZXV_E_FAULT dst does not have room in the RAM for the bank (with a compressed one, the program stops with an exception).

    zxv_report_error(n, "Cannot load stage 2");

Code bank errors#

A code bank is loaded into its region from its bridge, the first time one of its functions is called. A bridge cannot return an error, so if something goes wrong the program stops with report W, the message and the error code (in the machine's language):

Message Error When
"Bank a in use: cannot load b in its region" ZXV_E_ACCESS A function in a calls (directly or not) one in b, in the same region
"Bank b: the frame hook points into its region" ZXV_E_ACCESS The frame hook is in b's region
"Bank b: not loaded with interrupts off" ZXV_E_ACCESS b is called with interrupts off (from the frame hook, for example), and it is not loaded
"Too many nested bank calls" ZXV_E_RANGE More than 32 nested bank calls
"Bank b: the program changed: load it again" ZXV_E_CHANGED As in zxv_bank_load
"Bank b: it is damaged" ZXV_E_FORMAT As in zxv_bank_preload
"Bank b: it is not in the file" ZXV_E_NOENT The .zxv does not have that bank
"Bank b: the ROM has no banks" ZXV_E_ACCESS The ROM is older than specification 0.2
"Bank b: no card", "Bank b: no server for EXT:", "Bank b: cannot be read" ZXV_E_NOCARD, ZXV_E_OFFLINE, another Those of reading the file

For example: W Bank valley: it is damaged (-14), 0:1.

A bank fills its region from the start. Its variables start again on every load, and the region is filled with ebreak (c.ebreak, 0x9002) before it loads, so a call to something that is gone stops at once.

Ending a program and running others#

When a program ends (in whatever way), the memory belongs to BASIC again, so the BASIC program that was in it is lost. The ROM removes the frame hook, goes back to page 0 without scrolling or virtual playfield and silences both AY chips. The next .zxv starts with the usual colours, palettes and text.

zxv_exit_to_basic#

void zxv_exit_to_basic(int code);

Ends the program from anywhere, however deep inside it is, and returns to BASIC: the same as returning code from main. It does not return.

Parameters

Parameter Values What it is
code any int 0 means success: BASIC shows 0 OK, 0:1. Any other value means an error, and BASIC shows W Native code error (code), 0:1 (in Spanish, W Error en el código nativo (code), 0:1), with its sign if it is negative.

The value main returns works the same way. Native code called from BASIC with USR is different: what it returns is just the value of USR.

Example

if (!card_present())
    zxv_exit_to_basic(2);           /* W Native code error (2), 0:1 */

Since: specification 0.1 · function no. 19.

See also: zxv_report_error.

zxv_report_error#

void zxv_report_error(int code, const char *msg);

Ends the program and returns to BASIC with the report W and your own message instead of BASIC's. It does not return. The message is copied before BASIC takes back the memory, so it can be in a local array.

Parameters

Parameter Values What it is
code any int If it is not 0, it follows the message in brackets, with its sign. A ZXV_E_* error shows as it is: (-1).
msg UTF-8, up to 79 bytes The message. Whatever goes past 79 bytes is not shown (with a ROM older than specification 0.2, past 47). Empty (""), or NULL, leaves BASIC's usual text.

For example, zxv_report_error(5, "Fichero dañado") gives W Fichero dañado (5), 0:1; zxv_report_error(0, "No level files") gives W No level files, 0:1; and zxv_report_error(5, ""), W Native code error (5), 0:1.

Example

int size = zxv_file_load("level1.dat", level, sizeof level);

Graphics engine#

Declared in zxv_gfx.h. See Graphics for the explanations and the longer examples. All functions draw on the current target (the drawing page or a bitmap in memory) and clip to it and to the clip rectangle. The result is defined pixel by pixel by the ROM code: the emulator and the machine draw exactly the same pixels.

Common behaviour. No engine function returns an error. What goes beyond what is accepted is always handled the same way:

Case What the ROM does
Coordinates outside the target or the clip rectangle Clips: only what falls inside is drawn. Coordinates are signed, so a shape or a sprite can be half outside. Nothing is ever written outside the target.
A colour above 15 or negative Its 4 low bits are used (c & 15): 16 is 0 and −1 is 15. Except paper in zxv_gfx_pattern and out in zxv_m7_draw_map, where it counts as ZXV_CLEAR.
A size of 0 or negative, a NULL pointer or a sprite that does not come from zxv_spr_prepare Draws nothing (what each function does, in its entry).
A bitmap, tiles or a prepared sprite not aligned to 4 bytes Not checked: the engine reads and writes 32-bit words, and an unaligned access stops the program.
A bitmap whose pix, stride, w or h do not match its memory Not checked: it writes wherever they say.

When a program starts (and each time zxv_exec starts another one), the target is the drawing page 0, without a clip rectangle and without a pattern. zxv_cls, zxv_plot and the text do not use the engine: they always draw on the drawing page, even when the target is a bitmap, and ignore the clip rectangle and the pattern.

Types#

typedef struct {            /* a bitmap */
    uint8_t *pix;           /* first pixel, aligned to 4 */
    uint16_t stride;        /* bytes per line, a multiple of 4 */
    uint16_t w, h;          /* in pixels */
    uint16_t reserved;
} zxv_bitmap;

typedef struct {            /* a tile map */
    const uint16_t *cells;  /* cells, row by row */
    uint16_t w, h;          /* in cells */
    const uint8_t *tiles;   /* tile graphics, one after another (32 or 128 bytes) */
    uint8_t size;           /* tile side: 8 or 16 */
    uint8_t flags;          /* ZXV_MAP_WRAP */
} zxv_tilemap;

typedef struct {            /* a mode 7 texture */
    const uint8_t *texels;  /* 1 byte per texel (0-15), row by row */
    uint8_t log2size;       /* side = 2^log2size (1 to 10) */
    uint8_t wrap;           /* not 0: repeats; 0: outside is colour 'out' */
    uint8_t out;
    uint8_t flags;          /* ZXV_M7_TRANSPARENT; formerly 'reserved', 0 */
} zxv_m7tex;

typedef struct { int32_t u, v, du, dv; } zxv_m7line;   /* 16.16 fixed point */

typedef struct {            /* a rotated and scaled plane, 16.16 fixed point */
    int32_t x, y;           /* the point of the plane that goes at the centre */
    int32_t angle;          /* 0x10000 = a full turn, clockwise */
    int32_t zoom_x, zoom_y; /* scale on each axis of the plane: 0x10000 = 1 */
    int16_t cx, cy;         /* the centre, on the target (integers) */
} zxv_m7aff;

typedef struct {            /* a mode 7 camera, 16.16 fixed point */
    int32_t x, y;           /* position on the plane */
    int32_t height;         /* height above the floor */
    int32_t angle;          /* 0x10000 = a full turn; 0 looks towards growing u */
    int32_t focal;          /* focal distance, in pixels (also 16.16) */
    int16_t horizon;        /* target line of the horizon (integer) */
    int16_t reserved;
} zxv_m7cam;

Pixels are 4 bits, two per byte, the even pixel in the low 4 bits, as in VRAM. A bitmap w pixels wide needs at least w / 2 bytes per line, rounded up to a multiple of 4: a 64 × 32 bitmap has 32 bytes per line and 1,024 bytes. Bitmaps, tiles and prepared sprites must be aligned to 4 bytes (an array of uint32_t always is).

An 8 × 8 tile is 32 bytes (4 per line) and a 16 × 16 one, 128 (8 per line), one after another in tiles: tile n starts at tiles + n·32 or tiles + n·128. A map cell is a 16-bit number with the tile number and its attributes (the ZXV_CELL_* constants, below).

Target and clipping#

Where drawing goes: the drawing page (by default) or a bitmap in memory, and the clip rectangle inside it.

zxv_gfx_target#

void zxv_gfx_target(const zxv_bitmap *b);

Makes bitmap b the target: from now on, the whole engine draws on it. With NULL (or 0), the target goes back to the drawing page. It always removes the clip rectangle. The structure is copied, so it can be a local variable; the pixels are not, of course: they must stay there while drawing on them.

Parameters

Parameter Values What it is
b a bitmap, or NULL The new target. NULL: the drawing page, with whatever size it has at each moment (see zxv_gfx_draw_page).

Out of range

Case What the ROM does
b->pix is NULL, or w or h is 0 Accepts it, but nothing is drawn until the target changes.
pix not aligned to 4, stride not a multiple of 4 or smaller than w / 2 Not checked (see Common behaviour).

Example

static uint32_t buf_pix[64 * 32 / 8];           /* 64 x 32 pixels, aligned to 4 */
const zxv_bitmap buf = { (uint8_t *)buf_pix, 32, 64, 32, 0 };
zxv_gfx_target(&buf);                           /* draw in memory */
zxv_gfx_rect(0, 0, 64, 32, 1);
zxv_gfx_circle(32, 16, 12, 6, 1);
zxv_gfx_target(0);                              /* the drawing page again */

zxv_gfx_draw_page#

void zxv_gfx_draw_page(int page);

Chooses the drawing page: the VRAM page on which the engine (when the target is the page), zxv_cls, zxv_plot and the text draw. It does not change the visible page (that is zxv_set_page), so it is used for double buffering: draw on the page that is not shown and then show it. It does not touch the target: if it is a bitmap, the engine keeps drawing on it. Nor does it remove the clip rectangle.

The page size follows the video mode and ZXV_V_VSIZE on every call to the engine: 256 × 192 in mode 0 (or the one from ZXV_V_VSIZE, see Video registers) and 512 × 384 in mode 1.

Parameters

Parameter Values What it is
page 0 or 1 The page: 0 at ZXV_VRAM0_BASE and 1 at ZXV_VRAM1_BASE.

Out of range

Case What the ROM does
Another value Its low bit counts (page & 1): 2 is page 0 and −1, page 1.

Example

int visible = 0;
for (int frame = 0; zxv_key_get() < 0; frame++) {
    int hidden = 1 - visible;
    zxv_gfx_draw_page(hidden);                  /* draw on the one not shown */
    zxv_cls(0);
    zxv_gfx_circle(frame % 256, 96, 20, 6, 1);
    zxv_set_page(hidden);                       /* and show it */
    zxv_wait_vblank();
    visible = hidden;
}
zxv_set_page(0);
zxv_gfx_draw_page(0);

zxv_gfx_clip#

void zxv_gfx_clip(int x0, int y0, int x1, int y1);

Limits the engine's drawing to the rectangle from (x0, y0) to (x1, y1), excluding x1 and y1, in target coordinates. What falls outside is not touched. The rectangle is stored as given and on every drawing it is intersected with the target, so it can go beyond it. It lasts until the next zxv_gfx_clip or zxv_gfx_target (which removes it); zxv_gfx_draw_page does not change it.

Parameters

Parameter Values What it is
x0, y0 any integer The top left corner, included.
x1, y1 any integer The bottom right corner, excluded: the rectangle is x1 − x0 × y1 − y0.

Out of range

Case What the ROM does
x1 <= x0 or y1 <= y0, or the rectangle does not touch the target Accepts it: nothing is drawn until the clip rectangle changes.

To remove the clip rectangle without changing the target, set the same target again: zxv_gfx_target(0) (or whichever bitmap it was).

Example

zxv_gfx_clip(0, 0, 256, 160);           /* the score panel, below, is not touched */

zxv_gfx_pattern#

void zxv_gfx_pattern(const uint8_t *pat, int paper);

Sets an 8 × 8 pattern for the shapes: zxv_gfx_line, zxv_gfx_rect, zxv_gfx_tri, zxv_gfx_poly and zxv_gfx_circle. Where the pattern has a 1 the shape's colour is painted, and where it has a 0, colour paper, or nothing with ZXV_CLEAR. The pattern is anchored to the target: pixel (x, y) uses bit 7 − (x mod 8) of pat[y mod 8], so two shapes that touch match up. Filling with a pattern costs the same as with a plain colour. On lines and outlines, how it shows depends on where each pixel falls: a 45° diagonal over a checkerboard comes out all one colour.

The pattern is copied: pat can be a local variable. It lasts until the next call; every program starts with no pattern. It does not affect copies, sprites, maps or mode 7, nor zxv_cls, zxv_plot or the text.

Parameters

Parameter Values What it is
pat 8 bytes, or NULL One row per byte, from top to bottom; bit 7 is the leftmost pixel. NULL (or 0): back to plain colour.
paper 0–15, or ZXV_CLEAR The colour of the zeros of the pattern, or ZXV_CLEAR not to paint them (what is underneath shows). Not used when pat is NULL.

Out of range

Case What the ROM does
paper negative or greater than 15 Like ZXV_CLEAR: the zeros are not painted.
With a ROM of specification 0.1 The function does not exist: it does nothing and shapes come out plain.

Example

static const uint8_t check[8] = { 0xAA, 0x55, 0xAA, 0x55, 0xAA, 0x55, 0xAA, 0x55 };
zxv_gfx_pattern(check, 0);              /* checkerboard of the shape's colour and black */
zxv_gfx_rect(16, 16, 96, 64, 2);
zxv_gfx_pattern(check, ZXV_CLEAR);      /* here, what is underneath shows between the dots */

zxv_gfx_pattern(0, 0);                  /* plain colour again */

Sprites#

A prepared sprite is a picture with its mask already worked out, to draw it with a transparent 8, 8 pixels at a time. It is made once with zxv_spr_prepare and drawn as many times as needed. Its internal format belongs to the ROM: a sprite is used only with these functions.

zxv_spr_prepare#

uint32_t zxv_spr_prepare(const zxv_bitmap *src, int sx, int sy, int w, int h, void *buf);

Converts the rectangle (sx, sy) of w × h pixels of src into a prepared sprite, in buf. Pixels of colour 8, and those of the rectangle that fall outside src, become transparent. With buf set to NULL it writes nothing and only says how big it is: that is how you ask for the size first.

Parameters

Parameter Values What it is
src a bitmap The picture. It is also needed to ask for the size.
sx, sy any integer The corner of the rectangle in src.
w, h 1–1024 The size of the sprite.
buf memory aligned to 4, or NULL Where it is written, with room for what it returns (not checked).

Returns: the size of the sprite in bytes, 8 + h × ⌈w / 8⌉ × 8 (264 for a 16 × 16 one), whether it wrote it or not; 0 if it cannot be prepared.

Out of range

Case What the ROM does
src is NULL, or w or h outside 1–1024 Returns 0 and writes nothing.
buf smaller than the size Not checked: it writes past the end.

Example

static uint32_t sheet_pix[32 * 16 / 8];         /* two 16 x 16 pictures */
const zxv_bitmap sheet = { (uint8_t *)sheet_pix, 16, 32, 16, 0 };
static uint32_t ship[264 / 4];                  /* 8 + 16 · 2 · 8 bytes */
uint32_t n = zxv_spr_prepare(&sheet, 0, 0, 16, 16, NULL);    /* 264 */
if (n && n <= sizeof ship)
    zxv_spr_prepare(&sheet, 0, 0, 16, 16, ship);

Since: specification 0.1 · API function no. 36.

See also: zxv_spr_draw, zxv_gfxf_sprite, Graphics: sprites.

Tile maps#

A map is an array of cells; each cell says which tile goes in it and with which attributes (mirroring, transparency and priority). See Graphics: tile maps.

zxv_map_draw#

void zxv_map_draw(const zxv_tilemap *m, int mx, int my, int x, int y, int w, int h, int filter);

Draws, in the rectangle (x, y) of w × h pixels of the target, the part of the map that starts at pixel (mx, my) of the map: pixel (X, Y) of the target shows pixel (mx + X − x, my + Y − y) of the map. Each cell goes with its mirroring, and with ZXV_CELL_TRANSP its colour 8 shows what is underneath. With the filter, only the cells with priority or only those without it are drawn: a typical frame is the background (ZXV_MAP_BACK), the sprites and the front part (ZXV_MAP_FRONT). Cells that are not drawn (because of the filter or because they fall outside a map that does not repeat) leave what was there. With opaque tiles without mirroring and aligned to 8 pixels, it takes a faster path.

Parameters

Parameter Values What it is
m a map The map, with size 8 or 16 and w and h of 1 or more.
mx, my any integer The pixel of the map that goes at the corner of the rectangle. If the map repeats (ZXV_MAP_WRAP), it wraps round in both directions, also with negative values.
x, y any integer The corner of the rectangle on the target.
w, h 1 or more The size of the rectangle.
filter ZXV_MAP_ALL, ZXV_MAP_BACK or ZXV_MAP_FRONT Which cells are drawn.

Out of range

Case What the ROM does
m is NULL, its w or its h is 0, or size is neither 8 nor 16 Nothing.
w or h is 0 or less Nothing.
The visible part crosses more than 136 columns of tiles (more than about 1,080 pixels of width with 8-pixel tiles) Nothing. It does not happen on the machine's pages (up to 1,024 wide).
filter with another value Like ZXV_MAP_ALL.
A cell with a tile number that is not in tiles Not checked: it reads whatever lies beyond.

Example

static uint32_t tiles[2 * 8];                   /* two 8 x 8 tiles (32 bytes each) */
static uint16_t cells[32 * 24];
for (int i = 0; i < 8; i++) {
    tiles[i] = 0x11111111u;                     /* tile 0: plain blue */
    tiles[8 + i] = i & 1 ? 0x66666666u : 0x44444444u;   /* tile 1: stripes */

for (int i = 0; i < 32 * 24; i++)
    cells[i] = i / 32 == 23 ? 1 : 0;            /* the last row, the ground */
const zxv_tilemap map = { cells, 32, 24, (const uint8_t *)tiles, 8, ZXV_MAP_WRAP };

Mode 7#

Mode 7 draws a plane, a texture or a tile map, with its own transformation on each line of the target: rotated, scaled or in perspective, as on the SNES. Each line (zxv_m7line) holds the position on the plane (u, v) of pixel x = 0 of the target and the step (du, dv) per pixel, in 16.16 fixed point (65536 = one texel or one map pixel): pixel x of the line shows the point (u + x·du, v + x·dv), taking the integer part of each coordinate. zxv_m7_camera and zxv_m7_affine work out those lines; they can also be written by hand. See Graphics: mode 7.

With a texture it costs about 15 cycles per pixel (the whole mode 0 screen, a third of the frame); with a map, about 36 according to the specification (about 33 have been measured on the board). In mode 1 at full screen it does not fit in a frame: draw only the floor.

zxv_m7_draw#

void zxv_m7_draw(const zxv_m7tex *t, const zxv_m7line *l, int y, int n);

Draws n lines of a texture from line y of the target: line y + i uses l[i]. Each line covers the whole width of the clip rectangle. Coordinates are taken as unsigned: negative values fall outside the texture. If the texture repeats, everything falls inside (negative values too, which wrap round); if not, the outside is colour out. With ZXV_M7_TRANSPARENT in flags, texels of colour 8 are not drawn (nor is the outside if out is 8).

Parameters

Parameter Values What it is
t a texture Its texels (one byte per texel, 0–15, row by row), its log2size (1–10: from 2 × 2 to 1024 × 1024), wrap, out (0–15) and flags. Up to 256 × 256 (64 KB) fits in the user RAM.
l n lines The transformation of each line.
y any integer The first line of the target. Those that fall outside the clip rectangle are not drawn.
n 1 or more How many lines.

Out of range

Case What the ROM does
t or l is NULL, or n is 0 or less Nothing.
log2size outside 1–10 Nothing.
A texel or out above 15 Its 4 low bits.
flags with ZXV_M7_TRANSPARENT on a ROM of specification 0.1 The field was reserved and had to be left at 0: do not use it without first checking zxv_api_version ≥ 2.

Example

static uint8_t texels[64 * 64];                 /* a 64 x 64 board */
static zxv_m7line rows[192];
for (int v = 0; v < 64; v++)
    for (int u = 0; u < 64; u++)
        texels[v * 64 + u] = ((u / 8) ^ (v / 8)) & 1 ? 12 : 4;

    rows[i] = (zxv_m7line){ 0, i << 16, 0x4000 + i * 256, 0 };

.gfx graphics files#

Declared in zxv_gfxfile.h. They read .gfx files (those from png2gfx.py, zxv-gfx, the editor on the machine and BASIC's LOAD "x" GRAPHICS) already in memory. They are not in the ROM: they are built from gfxfile.c, which goes inside the program (add it to its sources), so they work with any ROM. The explanations and a complete example are in Graphics.

typedef struct {
    const uint8_t *data;
    uint32_t size;
} zxv_gfxfile;

The file can be anywhere: read with zxv_file_load or inside the program. The objects in the file are not aligned, so each function copies its object into buf, which must be aligned to 4, and returns the bytes buf needs, whether it copied them or not. If buf is NULL or room is smaller, it copies nothing: that is how you ask for the size. If the object is not there, or zxv_gfxf_open did not accept the file, it returns 0 (or NULL). None of them calls the ROM.

zxv_gfxf_open#

int zxv_gfxf_open(zxv_gfxfile *f, const void *data, uint32_t size);

Checks that data is a whole, well-formed .gfx file and leaves f ready for the other functions. It looks at the signature, the version and all the objects: that they fit in size and that each one has the length its dimensions say. Objects of kinds it does not know are skipped. The file is not copied: it must stay in data while f is in use.

Parameters

Parameter Values What it is
f a zxv_gfxfile What gets filled in.
data the file in memory From its first byte (ZXVG).
size bytes How big it is.

Returns: 1 if it accepts it; 0 if not, and then f is left empty (all the other functions give 0 or NULL with it).

When it returns 0

Case Why
size less than 8, no ZXVG at the start or a version other than 1 It is not a .gfx it understands.
An object goes beyond size The file is cut short (it was not read whole: check the max of zxv_file_load).
A sprite with a side of 0 or more than 1024, tiles that are neither 8 nor 16 or with none, an empty map or one with tiles that are neither 8 nor 16, a texture with log2size outside 1–10, a screen with a mode, border or flags that are not valid, or any of them with a length that does not match its dimensions The object is not valid.

Example

The .gfx format#

The 4 letters ZXVG, a version byte (1), a byte set to 0 and the number of objects (16 bits). Each object has an 8-byte header (kind, 0, number in 16 bits and length of its data in 32 bits) followed by its data. All numbers are little-endian.

Kind Object Data
1 Sprite Width and height (16 bits each, 1–1024) and its pixels: ⌈width / 2⌉ bytes per line
2 Tiles of S × S (S is the object's number: 8 or 16) How many (16 bits, 1 or more), 0 (16 bits) and the tiles (32 or 128 bytes each)
3 Map Width and height (16 bits each), tile side (8 or 16) and repetition (bytes), 0 (16 bits) and the cells (16 bits each)
4 Texture log2size (1–10), repetition, outside colour and flags (bit 0: 8 is transparent), one byte each, and the texels (one byte each)
5 Screen Mode (0 or 1), border colour, flags (bit 0: it has a palette) and 0, one byte each; if it has a palette, its 16 RGB565 colours (32 bytes); and the pixels of the page, as in VRAM (24,576 bytes in mode 0, 98,304 in mode 1)

Video registers#

At ZXV_VIDEO_REGS (0x2000_0400). Write them at any time: the system takes them just after each VBLANK and they show in the next frame.

Register Offset Size Contents
ZXV_V_MODE 0x00 8 bits Video mode, 0 or 1 (use zxv_set_mode, which also clears the drawing page)
ZXV_V_PAGE 0x01 8 bits Visible page, 0 or 1 (use zxv_set_page)
ZXV_V_BORDER 0x02 8 bits Border colour, 0–15 (not remapped; shown with the palette of the ZXV_V_REMAP table)
ZXV_V_FLAGS 0x03 8 bits ZXV_VFLAG_LINETAB (0x01): use the line table; ZXV_VFLAG_BLANK (0x02): show only the border
ZXV_V_SCROLL_X 0x04 16 bits Horizontal scroll of the picture, wrapping round
ZXV_V_SCROLL_Y 0x06 16 bits Vertical scroll, wrapping round
ZXV_V_REMAP 0x08 8 bits Colour remapping table in use, 0–3
ZXV_V_VSIZE 0x09 8 bits Page size in mode 0 (see below). Every program starts with 0
ZXV_V_OUT_INFO 0x0C 32 bits Read only: the video output (see below)

With scroll, screen pixel (x, y) shows page pixel ((x + SCROLL_X) mod width, (y + SCROLL_Y) mod height).

The output (ZXV_V_OUT_INFO). The user chooses it on the machine; programs only read it:

Bits Constants Contents
0–3 ZXV_OUT_DVI (1), ZXV_OUT_HDMI (2) The kind of output: DVI, with no sound through the cable, or HDMI, with sound. Other values, reserved
8–15 The refresh rate in Hz: always 60
16–17 ZXV_OUT_SCREEN_MASK (3 << 16), ZXV_OUT_SCREEN_SHIFT (16) The monitor, through the HDMI detection line: ZXV_OUT_SCREEN_UNKNOWN (0 << 16), not known (on a protoboard, or until one is connected); ZXV_OUT_SCREEN_NONE (1 << 16), it was connected and has been unplugged; ZXV_OUT_SCREEN_ON (2 << 16), connected. The emulator always says ZXV_OUT_SCREEN_ON 
uint32_t o = *(volatile uint32_t *)(uintptr_t)ZXV_V_OUT_INFO;
int hdmi = (o & 15) == ZXV_OUT_HDMI;
int screen_on = (o & ZXV_OUT_SCREEN_MASK) == ZXV_OUT_SCREEN_ON;

Page sizes (ZXV_V_VSIZE, mode 0 only; ignored in mode 1). When a .zxv is loaded, the ROM sets it to 0:

Constant Value Page Bytes per line
ZXV_VSIZE_SCREEN 0 256 × 192 128
ZXV_VSIZE_2X2 1 512 × 384 256
ZXV_VSIZE_WIDE 2 1024 × 192 512
ZXV_VSIZE_TALL 3 256 × 768 128

With ZXV_VSIZE_SCREEN in mode 0, each page shows only its first 24 KB; the 72 KB behind them (ZXV_VRAM_HIDDEN, ZXV_VRAM_HIDDEN_SIZE) are memory for the program (ZXV_VRAM0_DATA, ZXV_VRAM1_DATA; see How the SDK lays out a program), which is lost on switching to mode 1 or to another page size.

Remapping tables: four tables of 16 bytes from ZXV_REMAP_TABLES (table t at ZXV_REMAP_TABLES + 16·t). Entry v is the colour shown for pixel value v. The ROM sets them to the identity when each program starts.

Palettes: each table has its own, 16 RGB565 colours (u16) from ZXV_PALETTE(t) (ZXV_PALETTES + 32·t, at 0x2000_0480). A pixel of value v on a line that uses table t is shown in colour palette[t][table[t][v]]. They start with the usual colours (ZXV_STD_RGB565(i)), and the ROM sets them again when each program starts. Like the tables, they are read just after each VBLANK. To make colours, ZXV_RGB(r, g, b) (see Palette).

Line table: at ZXV_LINE_TABLE, one entry of ZXV_LINE_ENTRY_SIZE (8) bytes per line of the whole frame, border included, from the first line of the top border: 240 lines in mode 0 (the picture starts at line 24) and 480 in mode 1 (the picture, from line 48): ZXV_FRAME_LINES(mode) and ZXV_BORDER_LINES(mode). The frame is ZXV_FRAME_W × ZXV_FRAME_H (640 × 480), with a border of ZXV_BORDER_X (64) pixels at each side and ZXV_BORDER_Y (48) lines above and below (half that, in mode 0 pixels). It is only used with ZXV_VFLAG_LINETAB.

Offset Size Field Value for "as usual"
ZXV_LT_BORDER (0) 8 bits Border colour 0xFF (the one in ZXV_V_BORDER)
ZXV_LT_REMAP (1) 8 bits Remapping table 0xFF (the one in ZXV_V_REMAP)
ZXV_LT_SCROLL_X (2) 16 bits Horizontal scroll (0 to page width − 1) 0xFFFF (the one in ZXV_V_SCROLL_X)
ZXV_LT_SRC_LINE (4) 16 bits Page line shown (0 to page height − 1) 0xFFFF (= (y + SCROLL_Y) mod height)
6 16 bits Reserved, write 0

On border lines only the border field counts.

When changes are safe: right after each VBLANK the system reads the visible page, the registers and the tables. While bit ZXV_SYSF_LINK_BUSY of ZXV_SV_SYSFLAGS is 1 (up to 1.5 ms in mode 0 and 6 ms in mode 1 or with a large page), do not write to the visible page or the line table. The page that is not shown can be written at any time.

Video memory: ZXV_VRAM0_BASE (0x2000_4000) and ZXV_VRAM1_BASE (0x2001_C000), ZXV_VRAM_PAGE_SIZE (96 KB) each. Mode 0 uses the first 24,576 bytes of each page with ZXV_VSIZE_SCREEN, and mode 1, all 98,304. The picture sizes: ZXV_MODE0_W × ZXV_MODE0_H (256 × 192) and ZXV_MODE1_W × ZXV_MODE1_H (512 × 384).

The ROM reads them from the platform on a cold start and passes them to it when they change; with an older firmware, they start at 0 every time the machine is switched on.

The processor is a 32-bit RISC-V (RV32IMAC with the Zba, Zbb, Zbs, Zbkb and Zcb extensions, -march=rv32imac_zicsr_zifencei_zba_zbb_zbs_zbkb_zcb -mabi=ilp32), little-endian. Unaligned accesses to 16- or 32-bit data stop the program. Programs may turn interrupts on and off (bit 3 of mstatus) and read mcycle/minstret; other control registers belong to the system.

How the SDK lays out a program#

zxv.ld puts, from 0x2003_4000: the code (starting with crt0.S), the constants, the initialised variables, then the zeroed variables (BSS). It defines these symbols:

Symbol Meaning
__image_end End of what is stored in the .zxv
__bss_start, __bss_end The zeroed variables (the system clears them before starting)
__heap_start, __heap_end Free memory for picolibc's malloc: from the end of the BSS to 32 KB below the end of the user RAM
__tls_base Thread variables (picolibc's errno)
__vram0_start, __vram0_end, __vram1_start, __vram1_end What is declared with ZXV_VRAM0_DATA and ZXV_VRAM1_DATA: in the hidden VRAM of each page, from ZXV_VRAMn_BASE + ZXV_VRAM_HIDDEN (72 KB, ZXV_VRAM_HIDDEN_SIZE); crt0.S clears it

What is declared with ZXV_VRAM0_DATA or ZXV_VRAM1_DATA (for example, ZXV_VRAM0_DATA static uint8_t heights[18 * 1024];) does not go in the file: it starts at zero and cannot have another initial value (elf2zxv.py rejects it). It is lost if the program switches to mode 1 or uses another page size (ZXV_V_VSIZE), which take up the whole page, and a program that uses it cannot start in mode 1.

The stack is the system's: it starts near ZXV_URAM_END and grows down.

The .zxv file format#

A 72-byte header, followed by the loading screen, if there is one, and the program image, which is copied to the load address; after it, if there are any, the banks. All numbers are little-endian.

Offset Constant Size Field
0x00 ZXV_H_MAGIC 4 bytes ZXV1 (ZXV_HDR_MAGIC, 0x3156585A)
0x04 ZXV_H_HDR_SIZE 16 bits Header size: 72 (ZXV_HDR_SIZE)
0x06 ZXV_H_PROFILE 16 bits Specification profile: 1 (ZXV_HDR_PROFILE)
0x08 ZXV_H_LOAD 32 bits Load address
0x0C ZXV_H_ENTRY 32 bits Entry point
0x10 ZXV_H_IMAGE_SIZE 32 bits Size of the image
0x14 ZXV_H_BSS_SIZE 32 bits Bytes cleared to zero after the image (including the regions of the code banks)
0x18 ZXV_H_STACK 32 bits Stack top (0 = keep the system's stack)
0x1C ZXV_H_MODE 8 bits Initial video mode (its bit 0 counts)
0x1D ZXV_H_FLAGS 8 bits Reserved: written as 0, ignored when loading
0x1E 16 bits Reserved
0x20 ZXV_H_CRC 32 bits CRC-32 of the image (the zlib one)
0x24 ZXV_H_NAME 28 bytes Name (ASCII, zero-terminated)
0x40 ZXV_H_SCREEN 32 bits Size of the loading screen, which comes after the header (0 = none)
0x44 32 bits Reserved (0)

When loading it, the ROM checks:

Check If not
The signature, the header size (72) and the profile (1) ZXV_E_FORMAT
That the load address is aligned to 4 and the entry point is even and inside the image ZXV_E_FORMAT
That the image and the BSS start in the user RAM and fit leaving 4 KB below the ROM's stack ZXV_E_RANGE
That a stack top other than 0 is aligned to 16 and lies between the end of the BSS and ZXV_URAM_END ZXV_E_RANGE
The loading screen, if there is one (below) ZXV_E_FORMAT
That the whole image is read, and its CRC ZXV_E_FORMAT

Then it clears the BSS, sets the video mode (if the loading screen is not already in that mode; if it is, the program starts with it on page 0), sets ZXV_V_VSIZE to 0 and calls the entry point as int entry(void). Before loading, it leaves the graphics engine on page 0 with no clip rectangle or pattern, and the colours and the text as at the start. A .zxv with the old 64-byte header does not load (ZXV_E_FORMAT): run it through elf2zxv.py again.

The loading screen#

It is the data of a screen object of a .gfx, ZXV_SCREEN_SIZE_F(mode, flags) bytes long:

Offset Size Field
0 8 bits Mode, 0 or 1
1 8 bits Border colour, 0–15
2 8 bits Flags: ZXV_SCREEN_F_PALETTE (0x01), it has a palette; the others, 0
3 8 bits 0
4 32 bytes With a palette, its 16 RGB565 colours (ZXV_SCREEN_PALETTE, 32)
4 or 36 24,576 or 98,304 bytes The pixels of the page, as in VRAM (ZXV_SCREEN_PIXELS(mode))

ZXV_SCREEN_HEAD (4) is the size of the screen's header; ZXV_SCREEN_SIZE(mode), that of a screen without a palette, and ZXV_SCREEN_SIZE_F(mode, flags), that of the whole screen. The ROM checks that the mode, the border, the flags and the 0 are valid and that the size in ZXV_H_SCREEN is exactly that; if not, ZXV_E_FORMAT. It puts it up before loading the image, with its mode, its border (with no scroll or remapping) and, if it has one, its palette in table 0.

The banks#

The banks go after the image, which the loader ignores (so older ROMs load the program all the same). At the end of the file comes the trailer, ZXV_BANK_TAIL (16) bytes long:

Offset Constant Size Field
0 ZXV_BANK_MAGIC 8 bytes ZXVBANK1
8 ZXV_BANK_T_INDEX 32 bits Where the index starts, from the start of the file
12 ZXV_BANK_T_INDEX_LEN 32 bits The length of the index

The index: a header of ZXV_BANK_HEAD (16) bytes and an entry of ZXV_BANK_ENTRY (48) bytes per bank.

Offset Constant Size Field
0 ZXV_BANK_I_COUNT 32 bits How many banks
4 ZXV_BANK_I_PROG_CRC 32 bits The CRC of the program's image (its fingerprint)
8 ZXV_BANK_I_IMAGE_SIZE 32 bits The size of the image
12 ZXV_BANK_I_CRC 32 bits The CRC of the entries

Each entry:

Offset Constant Size Field
0 ZXV_BANK_E_NAME 16 bytes Name (ASCII, up to ZXV_BANK_NAME_MAX, 15, zero-terminated)
16 ZXV_BANK_E_KIND 8 bits ZXV_BANK_DATA (0) or ZXV_BANK_CODE (1)
17 ZXV_BANK_E_METHOD 8 bits ZXV_BANK_STORED (0) or ZXV_BANK_DEFLATE (1, raw deflate without a wrapper, RFC 1951)
18 ZXV_BANK_E_REGION 8 bits The region, 0 to 7 (code banks)
20 ZXV_BANK_E_OFFSET 32 bits Where it starts, from the start of the file
24 ZXV_BANK_E_STORED 32 bits Its size in the file
28 ZXV_BANK_E_SIZE 32 bits Its real size
32 ZXV_BANK_E_CRC 32 bits CRC-32 of the real data
36 ZXV_BANK_E_ADDR 32 bits Code banks, where they go: the start of their region (they carry their code, constants, data and zeroed BSS)

The rest is reserved (0). If the .zxv ends in that trailer, the ROM keeps its file open while the program runs (ZXV_SV_PROG_FILE).

elf2zxv.py#

        [--stack ADDRESS] [--screen SCREEN] [--bank NAME=FILE ...] [--pack]

Converts a 32-bit RISC-V ELF, linked with sdk/zxv.ld, into a .zxv program: the header, the loading screen if there is one, the image and, after it, the banks. The SDK's Makefile calls it by itself.

Option Effect
--name NAME Name in the header: up to 27 ASCII characters (others come out as ?). By default, the output file name without the extension (what comes after the last /)
--mode 0\|1 Initial video mode (default 0)
--stack ADDRESS Stack top, in decimal or 0x...; default 0, the system's stack. It must meet the rules of the format or the program does not load

zxvbanks.py#

python3 sdk/tools/zxvbanks.py -o OUTPUT.zxv [--cc GCC] [--cflags "..."] [--sdk FOLDER]
        RESIDENT.c ... --code NAME[@REGION]=A.c,B.c ... [--bank NAME=FILE ...]
        [--pack] [--name NAME] [--mode 0|1] [--screen SCREEN]

Builds a program with code banks: functions that are not in memory all at once, but are loaded from the .zxv itself when they are called (see Banks). The resident part (what is always there) goes in RAM as usual; each bank is compiled separately and linked in its region, which is as big as its largest bank and goes after the BSS. The program calls the functions of a bank like any other: a resident "bridge" loads the bank if needed and jumps to the function.

Option Effect
-o OUTPUT.zxv The program to write (required)
RESIDENT.c ... The files of the resident part (.c, .S). The SDK's crt0.S, zxvlib.c, zxvbank.c and zxvbankcode.c are added by themselves
--code NAME[@REGION]=A.c,B.c A code bank and its files. The name, 1 to 15 letters, digits or _; the region, 0 to 7 (0 by default). It can be repeated; at least one is needed (without code banks, use elf2zxv.py)
--bank NAME=FILE A data bank, as in elf2zxv.py. It can be repeated
--pack Compresses the banks, as in elf2zxv.py
--name, --mode, --screen As in elf2zxv.py
--cc GCC The compiler (riscv64-unknown-elf-gcc by default); objcopy, nm, objdump and readelf, those with the same prefix
--cflags "..." The compiler options (by default, the SDK's: -march=... -mabi=ilp32 -Os -g -Wall -Wextra -std=gnu11 -ffreestanding ...), split as the system's command line does: on Windows, the \ of paths stay and quotes group (-I"C:\my stuff\include")
--sdk FOLDER The SDK folder (by default, the tool's)

It writes OUTPUT.zxv, OUTPUT.elf (for debugging) and, in OUTPUT.bancos/, the intermediate files and the symbols for GDB (gdb/residente.elf and gdb/BANK.elf, for zxvbanks-gdb.py). It stops if two banks have the same name or the same function, if a bank exports a variable (make it static or put it in the resident part: it would be wiped when another bank of its region is loaded), has thread variables or has variables in the hidden VRAM (ZXV_VRAM0_DATA, ZXV_VRAM1_DATA: declare them in the resident part, where they take no user RAM either). It warns if a bank takes the address of one of its functions: that pointer is valid only while the bank is loaded.

zxvbanks-gdb.py#

gdb-multiarch game.elf -x sdk/tools/zxvbanks-gdb.py -ex "target remote :1234"

A GDB script (or, once inside, source sdk/tools/zxvbanks-gdb.py) to debug a program with code banks: the banks of a region are at the same addresses, and GDB can only have one function per address. It uses game.bancos/gdb/residente.elf instead of the whole ELF and, every time a bank is loaded and every time the program stops, adds the symbols of the loaded banks and removes those of the others. So break FUNCTION in a bank stays pending until it is loaded and stops only in it, and bt, list and print work with what is really there. The bridges are called FUNCTION.puente. It adds the zxvbanks command, which shows the banks and which ones are loaded. With a program without code banks it does nothing.

--size S The longest side of the model, in world units (2 by default)
--keep-origin Does not centre it: the origin of the .obj stays as the model's
--mat NAME=DARK,LIGHT[,two][,flat][,decal] The colours (0–15) of a material, and its options: two, seen from both sides; flat, without light; decal, stuck on top of another face and drawn after it. It can be repeated
--default DARK,LIGHT The colours of faces without a material (1,9 by default: blue)
--two-sided All faces are seen from both sides
--bas Outputs ZX Basic: the arrays NAME_v and NAME_f and SUB NAME_model(n), which sets it as model n of MODEL3D

The colours of a face come from its material: one called zxv_DARK_LIGHT[_two][_flat][_decal] gives those; if not, the diffuse colour (Kd) from its .mtl, the closest of the 16 and its pair (bright and not bright); if not, --default. Non-convex faces and faces with more than 32 sides are split into convex pieces of up to 32 sides; faces with no area are dropped. It warns if there are more than 512 vertices (what zxv_3d accepts) or if a face crosses itself. It stops, with a message saying what and where, if a face uses a vertex that does not exist, if a vertex lacks its three numbers, if there are no vertices or faces, if some colours are not valid, if an option has no value or if --size is not a number greater than 0 or is too small. Comments (#) may go at the end of a line.

fontconv.py#

python3 sdk/tools/fontconv.py INPUT OUTPUT.c NAME [options]
python3 sdk/tools/fontconv.py INPUT OUTPUT.txt [options]

Converts bitmap fonts into C for zxv_font.h (NAME_n, NAME_h, NAME_codes[] and NAME_bits[]), or into text to touch them up by hand (if the output ends in .txt). It is explained in Fonts from elsewhere.

Input Format
.txt The ZX-V one (rom/font/zxv8x8.txt): == CODE and the rows, # ink and . background
.ch8, or 768 bytes ZX Spectrum: 96 characters, from 32 to 127 (its 0x5E is ↑, 0x60 £ and 0x7F ©)
.bin, .rom, .fnt, others A dump of 8 bytes per character (or --height): PC (CP437), MSX, Amstrad CPC...
.psf PC Screen Font 1 or 2 (the Linux console ones), with its Unicode table if it has one
.bdf Glyph Bitmap Distribution Format (X11)
.hex Like GNU Unifont: CODE:BYTES; wide characters (the 16-column ones) are left out, with a warning
Option Effect
--format F txt, zx, raw, psf, bdf or hex, if the extension (or the contents) is not enough
--first N raw: the code of the first character (0 by default; 32 if there are 96)
--height H raw: the rows of each character (8 by default). hex: those of the 8-column ones (by default, those of the narrowest in the file; if all have more than 16 bytes, it must be given)
--charset C raw: the Python character set used to turn codes above 127 into Unicode (cp437 if there are 256 from 0; otherwise latin-1)
--ascii zx: leaves ^, ` and 127 as in ASCII
--range R The characters that are kept, in hexadecimal: 20-7E,A0-FF by default (ASCII and Latin-1, with accents, ñ, ¿ and ¡)

Fonts must be up to 8 columns wide and 1 to 32 rows high, all the characters of --range the same (those outside do not count). It stops if more than 224 characters remain (what zxv_font holds; use --range) or none, or if a dump goes past code 255 (more than 256 characters from --first: usually a --height that is not the font's). A font's licence is still its own: being able to convert it does not mean you may distribute it.

mkweb.py#

python3 sdk/tools/mkweb.py OUTPUT GAME [FILE...] --kit KIT [options]
python3 sdk/tools/mkweb.py OUTPUT --config game.json [--kit KIT] [options]

Prepares a game for the web: a page that has only that game, which starts by itself and starts again when it ends, without BASIC being seen. To upload it to itch.io or any server; it also works opened from disk. It is explained, with the touch controls and game.json, in Publishing your game on the web.

Argument or option Effect
OUTPUT The folder of the page. It is created; if it already exists, it is deleted entirely first
GAME The program that starts: .zvb, .zxv, .tap, .tzx or a .bas listing (or .txt). If it is a .zxv or a .zvb with a loading screen, the page shows it while starting
FILE... What the game needs (.gfx, .pt3, .afb...): it goes with it on the ROM: drive, where BASIC finds it by itself. Names of up to 63 printable ASCII characters, without \ : * ? " < > \|, not repeated
--kit KIT The play/ folder of the web version (zxv-web.zip, or emulator/build-web/web/play): it must have index.html, play.js, play.css, engine.js and zxv-core.js. Required
--config game.json The options from a file (below)
--title TEXT The name on the cover and the tab (by default, the game's)
--id NAME The name of its card in the browser: letters, digits, - and _, up to 40 (by default, the game's). Changing it means starting with an empty card
--lang auto\|es\|en The language of the machine and the page (auto, the browser's, by default)
--border 0\|1\|2 The border: full (0, the default), small or none
--fit aspect\|integer\|fill How the picture is scaled (also proporcion, entera and llenar); aspect by default
--touch PRESET\|JSON The touch controls: joystick (the default), arrows, qaop or none, or a JSON file or text
--zip FILE.zip Also, the page in a .zip (with index.html at the root)
--kit-url URL Does not copy the kit: the page uses the one at URL (relative to it, like ../kit/). Only index.html and game.js go in the folder. Not compatible with --zip

game.json holds the same: start, files, title, id, lang, border, fit, touch, kit and kit_url, with paths relative to it; the command-line options override its own. It writes in OUTPUT the kit (with its licences), game.js (the game, the ROM: files and the options) and, with --kit-url, only index.html and game.js. It exits with code 1 and a message if something is not valid, and with 2 without arguments (it shows the help).

zxv-music#

zxv-music [--free KB] [--channels LIST] INPUT OUTPUT.zxm

Converts a PT3, a TurboSound (Pro Tracker 3 and Vortex Tracker II), a MOD, an S3M or an XM (up to 4 MB) to the own format, .zxm, and says what it could not carry over and how much the samples take in the sound memory. What it keeps of each format is in the guide.

Option Effect
--free KB Leaves that many KB (0–96) of the sound memory free for other samples, such as the sounds of SAMPLE in BASIC: the song's samples that do not fit go in ADPCM, at half the samples or, if even that fails, are left out
--channels LIST Of a MOD, S3M or XM, the channels to keep, up to 12, with the tracker's numbers, from 1 (1-8,11,13). Without it, of a module with more than 12 channels, the 12 that play the most notes are kept

It exits with code 2 if the options are not valid (or --channels with a PT3), and with 1 if it cannot read, convert or write.

zxv-link and zxv-link-gui#

zxv-link ports
zxv-link --port PORT info | send FILE [DEST] | run FILE [MORE...] | run --pc FILE | log
zxv-link --port PORT exec PATH | ls [PATH] | get PATH [FILE] | rm PATH | mv PATH NEW | mkdir PATH
zxv-link --port PORT serve [--folder FOLDER [--run PROGRAM]] [--basic-debug TCP_PORT] [FILE...]
zxv-link --port PORT [--yes] update zxv-update.bin
zxv-link --port MACHINE pair

Remote loading: they talk to the machine through the J5 header, with a 3.3 V USB-serial adapter, or over the network if the Pico CPU is a Pico 2 W. They send programs, run them, manage the files on the card, serve a folder on the PC as the EXT: drive and update the firmware. zxv-link-gui does the same with a window. How to use them is in Loading programs from the PC (J5) and over Wi-Fi.

Command Effect
ports The serial ports there are and the ZX-Vs on the network that answer, one per line on standard output, as --port takes them. Those that answer with another version of the network protocol are left out (they cannot be talked to): they go to standard error, after "Not compatible:", with their firmware and what to update, the machine or zxv-link
info The version of the firmware, the specification and the protocol, and whether the machine is waiting for a command or has a program running
send FILE [DEST] Sends the file to the card (with its name, or DEST)
run FILE [MORE...] Sends the file (and the ones it loads) to the card and runs it; if a program is running, it stops it first
run --pc FILE Runs it straight into memory, without copying it to the card: the machine reads it from the PC through EXT:. If the program keeps it open (a .zxv with code banks), it keeps serving it until the program ends or Ctrl+C, and writes the line zxv-link: serving-ext to standard output
exec PATH Runs what is already on the machine: SD:/games/a.zxv, ROM:/b.bas or EXT:/c.zxv
ls [PATH] What is in a folder of the card (SD:/ if none is given) or of ROM:
get PATH [FILE] Copies a file from the card (or from ROM:) to the PC
rm PATH Deletes a file or an empty folder
mv PATH NEW Renames or moves, on the same drive
mkdir PATH Creates a folder
log The machine's log, until Ctrl+C
serve ... Serves FOLDER as the EXT: drive until Ctrl+C (with --run, first runs PROGRAM, from inside the folder, from EXT:), and/or the BASIC debugger over TCP on TCP_PORT (used by the VS Code extension), after sending the FILEs. It needs --folder or --basic-debug; --run only with --folder and without --basic-debug
update FILE Updates the machine's firmware with a zxv-update.bin, without a card: the machine reads it from the PC. It shows the versions first and asks
pair Pairs this PC with a ZX-V on the network (with EDIT > Wi-Fi > Pair a PC open on it): both show a code and, if it matches, it is accepted on the machine
Option Effect
--port PORT The adapter (COM5 on Windows, /dev/ttyUSB0 on Linux) or a ZX-V on the network (its name, ZX-V-1A2B, or its IP). zxv-link ports lists them. Needed by every command except ports
--overwrite Also replaces on the card what zxv-link did not put there, and lets the machine replace or delete in the EXT: folder what it did not write itself
--yes update without asking
--lang es\|en The language of the messages (by default, the system's)

What is already on the card unchanged (the same size and the same CRC) is not sent again. It exits with code 2 if the command is not valid (it shows the help), with 3 if it cannot open the port, with 4 if it would have to replace on the card something it did not put there (without --overwrite), and with 1 if anything else fails.

The standard C library (picolibc)#

Programs compiled with picolibc and zxvc.c (see the guide) can use:

What Functions
Files fopen, fread, fwrite, fgets, fprintf, fseek, fclose..., and open, read, write, lseek, close
Folders opendir, readdir, rewinddir, closedir, mkdir, rmdir, chdir, getcwd
Names rename, unlink/remove, stat, fstat
Console printf, puts, getchar, fgets(..., stdin): the screen and the keyboard (with echo; Enter is '\n')
Memory malloc, free, realloc
Time time, gettimeofday, localtime: the machine's clock, local time (1 January 2026 at 0:00 if it is not set)
Exit exit, abort: back to BASIC (exit(0) gives 0 OK and any other code a W report, as in zxv_exit_to_basic)
  • API errors arrive in errno:
ZX-V code errno
ZXV_E_NOENT ENOENT
ZXV_E_EXIST EEXIST
ZXV_E_NAME, ZXV_E_INVAL EINVAL
ZXV_E_NOTDIR ENOTDIR
ZXV_E_ISDIR EISDIR
ZXV_E_NOTEMPTY ENOTEMPTY
ZXV_E_BADF EBADF
ZXV_E_MFILE EMFILE
ZXV_E_ACCESS EACCES
ZXV_E_FAULT EFAULT
ZXV_E_NOCARD ENODEV
ZXV_E_NOSPC ENOSPC
ZXV_E_FORMAT ENOEXEC
ZXV_E_RANGE ERANGE
The rest (ZXV_E_IO, ZXV_E_NOCLOCK, ZXV_E_OFFLINE, ZXV_E_CHANGED) EIO
  • Descriptors 0, 1 and 2 are the console; those of files are the API's plus 3.
  • Folders open at once, as in the API: ZXV_MAX_DIRS (4). rewinddir closes the folder and opens it again on the next readdir.
  • struct dirent has d_name, d_type (DT_DIR or DT_REG) and, as an extra, the size in d_size.
  • printf with decimals adds about 7 KB; -DPICOLIBC_INTEGER_PRINTF_SCANF when linking uses the smaller one, integers only.
  • The console speaks UTF-8, like C strings: printf("¿Qué tal?") shows the accents, and fgets gives the keys typed in UTF-8 (ñ is two bytes). Letters the ROM font does not have come out as ?.
  • The heap (malloc) goes from the end of the program to 32 KB below the end of the user RAM, where the stack is.
